# ESP32-CAM Dashboard Stream + Sensor Sleep

## Scope and verification

Standalone sketch based on the camera pins and backend registration contract in `origin/pooh` (`full-cam_test.ino`). No TFT code. This does not modify or switch your Git branch. RFID work is unchanged.

Built for AI-Thinker ESP32-CAM using PlatformIO espressif32 7.0.1 / Arduino-ESP32 2.0.17, and Arduino CLI with ESP32 core 3.3.10 (`esp32:esp32:esp32cam`). Arduino `.ino` preprocessing is included in the latter check. An explicit JpegCopy forward declaration and copyFrameLocked prototype prevent autogenerated prototypes from referring to an unknown custom type. Source-contract checks do not prove physical camera operation. Streaming, temperature, sleep/wake cycles and Dashboard rendering must be checked on the real board.

## Private settings

This repository example does not include private settings. Copy `cam_settings.example.h` to `cam_settings.h` beside the sketch, then configure it locally or copy your existing private header. Keep the existing DEVICE_TOKEN consistent with the backend. Do not upload the private header to GitHub or send its contents in chat.

Only the example header is tracked. The folder-local .gitignore excludes `cam_settings.h`. This is a standalone Arduino example outside PlatformIO src/, so it does not replace the existing pooh firmware entry point.

## Arduino IDE

1. Open `cam_dashboard_sleep.ino` as a standalone sketch. Keep `cam_settings.h` beside it. Do not combine with another sketch that defines setup/loop.
2. Select AI Thinker ESP32-CAM. Ensure PSRAM is enabled where the selected board offers that setting. No extra camera, TFT or ArduinoJson library is required.
3. Upload using the usual ESP32-CAM USB programmer/FTDI procedure. Remove GPIO0-to-GND boot jumper after upload and reset.
4. Open Serial Monitor at 115200. If this board is still physically wired over UART to the main board, disconnect that UART for this standalone ESP-NOW/Wi-Fi design: Serial here is debug output, not the old UART protocol.
5. Use a stable power supply appropriate to the ESP32-CAM board (normally regulated 5V at its 5V input), common GND and adequate current. Never apply 5V to an ESP32 GPIO. Do not disable brownout detection to conceal a power fault.

## URLs

Read the actual DHCP IP from `[WIFI] IP=...` in Serial Monitor. The addresses below are templates, not a claimed board IP:

- `http://<CAM_IP>/` - local test page with Start/Stop.
- `http://<CAM_IP>:81/stream` - MJPEG URL to enter in pooh Dashboard camera settings.
- `http://<CAM_IP>/capture` - one JPEG snapshot, matching the backend contract.
- `http://<CAM_IP>/status` - JSON status; does not wake the camera.

Only one MJPEG viewer at a time. Close the camera test page/stream before viewing through Dashboard. An `<img>` stream needs no CORS fetch permission, but browser local-network access policy may require user approval. An HTTPS Dashboard may block the HTTP camera as mixed content; this version targets a trusted local HTTP LAN, not public HTTPS deployment.

The integrated CctvMonitor accepts a stream URL from its settings icon and stores it in localStorage. Use the port-81 /stream URL, not /capture (which is a still image). Both admin and guard Dashboards now include the viewer and presence notice. No continuous recording is provided. Deploy the matching application changes; the firmware archive alone does not install them.

## Image and sleep behavior

- Camera starts powered down. A capture or stream request initializes it on demand.
- JPEG 640x480 with PSRAM; fallback 320x240 without PSRAM. Quality 10, one framebuffer. Up to 8 FPS by rate limiting, not a guaranteed measured rate.
- After the last request/stream disconnect, 30 seconds idle triggers camera driver deinit and sensor PWDN HIGH. Wi-Fi remains reachable. This is sensor standby, NOT ESP32 deep sleep.
- Streaming is limited to 120 seconds per connection, then sensor shutdown and a 10-second cooldown. Dashboard may hold the last frame or display an error after the stream ends: wait 10 seconds and press Refresh. No automatic reconnect loop is added.
- Cooldown applies only to /stream. Backend /capture requests bypass stream cooldown, so that policy does not deliberately discard entry evidence. Hardware, network, busy-lock or initialization failures can still lose a snapshot; this is not a capture guarantee. Explicit Serial manual sleep remains a maintenance override that disables all camera requests.
- Serial `s` requests persistent manual sleep; a running stream stops and cools down. Serial `w` clears that maintenance override: /capture can wake immediately, whereas /stream still waits for cooldown. These are not public unauthenticated HTTP mutation endpoints.
- ESP-NOW command 1 reports approach to the backend, and command 0 reports absence. Neither initializes the camera nor starts a stream. The callback only publishes atomic metadata; loop() debounces transitions for 300 ms and POSTs the latest stable state to /devices/cam/presence. On failure it retries the latest state no faster than every 3 seconds, using bounded HTTP waits. Repeated identical ESP-NOW commands do not repeatedly notify. This is best-effort latest-state delivery, not a durable offline event history; short events can be superseded while disconnected. Main and CAM must use the same Wi-Fi channel. Queuing a command on main does not prove CAM received it.
- A Dashboard /stream request wakes the sensor even with nobody nearby. A backend IN /capture request also wakes it; this is still required for entry evidence. OUT does not request a photo. An active viewer keeps the sensor awake until the stream budget ends. Command 0 shortens idle sleep to 5 seconds only when no stream/capture is active; normal idle timeout is 30 seconds if presence is unknown or last reported as present. Approach alone does not stream, capture, authorize or open the door.
- The flash LED remains off. This reduces activity but cannot guarantee a safe temperature. There is no measured temperature or thermal feedback. Provide ventilation; if the board becomes excessively hot, disconnect power and inspect supply/wiring before continuing.

## Backend

Backend and Dashboard retain the teammate's existing architecture. The presence-notification revision also needs the matching authenticated backend route, WebSocket event and admin/guard notification component. Keep DEVICE_TOKEN unchanged. The extra dashboard-only sketch and HTML test page are optional diagnostics, not replacements for the teammate's Dashboard; use this full CAM sketch to register and report presence.

Every 60 seconds and after Wi-Fi reconnection, POST `{ "ip": "..." }` to `<kServerBase>/devices/cam/register` with the existing DEVICE_TOKEN header. Registration failure is logged and does not prevent direct local streaming. The backend currently retrieves /capture without a camera-side credential; this sketch preserves that interface.

Presence contract:

- Device POST `/devices/cam/presence`, `Authorization: Bearer <existing DEVICE_TOKEN>`, JSON `{ "present": true }` or `{ "present": false }`. A server without this new route returns 404 and the CAM retries; update the application before flashing this revision.
- Authenticated Dashboard GET `/devices/cam/presence`: `{ "present": boolean | null, "reportedAt": ISO-string | null }`. This is the last reported state, not a reliable live occupancy count or main-board heartbeat.
- Existing ticket-authenticated WebSocket event `presence`: `{ "present": boolean, "reportedAt": ISO-string }`. Show a new approach notification for a true transition; the initial GET snapshot must not create a fresh arrival alert. Backend deduplicates unchanged-state reports. No schema migration or credential change is needed.
- `[PRESENCE] Notify present=true HTTP 201; sensor unchanged` is an example of successful device reporting, not proof the browser rendered its notification. Confirm the existing authenticated Dashboard receives the event separately, and verify /status remains asleep when approach is the only stimulus.

## Security limitation

/capture, /stream and /status are unencrypted and unauthenticated to match the existing direct Dashboard/backend design. Anyone who can reach the device on that LAN can view images or consume the single stream. Dashboard login alone does NOT protect the camera URL. Use a trusted isolated test LAN only; do not port-forward it. An authenticated same-origin proxy with HTTPS requires coordinated backend/frontend work and is not included in this standalone firmware.

## Hardware acceptance checklist

- The capture-priority revision releases the camera mutex and returns its framebuffer before any JPEG network transmission. Each response owns a separate JPEG copy (PSRAM when available), with a bounded allocation size. Live preview yields acquisition to queued capture requests. An entry request discards the queued old frame before acquiring its image. This removes a code-level contention hazard, not all possible camera/network failures.
- Wi-Fi modem power saving is disabled for control/capture responsiveness; camera sensor standby is unchanged. This can increase Wi-Fi power use and is not a thermal guarantee.
- `[CAPTURE] Request received` proves a request reached the camera, not that an access-log photo was saved. The following line reports either HTTP 503 with a specific acquisition/init/mutex/memory reason, or byte count, elapsed milliseconds and the actual send result. `[STREAM] End` separately reports acquisition versus HTTP-send failure, elapsed time and RSSI. A successful camera send still needs confirmation from the backend's photo-save log/history.
- Test `/capture` first with no stream, then while one Dashboard viewer is open. Finally scan IN and look for a new `[CAPTURE]` request. If none appears, inspect the existing backend's ImageFetchService warning and registered camera IP; do not assume a camera-side fix can repair a missing request. The existing pooh fetch timeout is 4 seconds and is not changed by this sketch.
- Boot prints PSRAM=yes and actual IP, without reset/brownout errors.
- Before opening any stream/capture URL, /status initially says asleep. Approach the main sensor: CAM should report `[PRESENCE] Notify present=true HTTP 201; sensor unchanged`, the authenticated Dashboard should show the notification, and /status should still say asleep. Keep the Dashboard camera URL cleared during this check.
- Move away and check the latest false report and timestamp. Approach again: expect a new true notification. Repeated unchanged reports must not produce repeated arrival notifications. Initial page load shows the last sensor report without creating a fresh arrival notification.
- Open the Dashboard camera viewer with its saved /stream URL: the sensor should wake. Close the viewer and wait for standby before testing approach alone again. Finally, /capture should return a real JPEG.
- Stream moves on the local page, then on Dashboard after closing the local viewer.
- Close stream; after 30 seconds /status says asleep. /capture wakes it again.
- Repeat sleep/wake several times and verify no corrupted JPEG or reset.
- Observe the 120-second limit and 10-second cooldown; test Refresh after cooldown.
- Confirm [REGISTER] HTTP 200/201 when backend is running; verify entry photo capture separately.
- Confirm real temperature behavior/ventilation. Do not claim thermal safety from compilation or the timeout alone.
